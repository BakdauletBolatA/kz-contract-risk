# План проекта и чекпоинты

Проект: первичный скрининг договоров аренды, поставки и подряда для малого
бизнеса РК. Система находит пункты, невыгодные **для конкретной стороны**
(арендатор, покупатель, заказчик, подрядчик…), объясняет риск простым языком,
показывает, как такое условие обычно звучит в рыночной практике, и предлагает
более безопасную формулировку.

Это не замена юристу. Это фильтр, который за минуту показывает, на какие
пункты стоит потратить время юриста — или хотя бы собственное внимание.

---

## Главное решение о порядке работ

Исходный порядок из постановки задачи — корпус → правила → RAG → LLM → eval →
отчёт. Здесь eval сдвинут **до** системы: сначала фиксируются руководство по
разметке, формат эталона, метрики и замороженный датасет, и только потом
пишется первое правило. Причина та же, что в прошлых RAG-проектах: харнесс,
написанный после системы, неизбежно подгоняется под неё — метрику выбирают ту,
на которой система выглядит хорошо, а разметку «уточняют» после взгляда на
выдачу.

Второе решение: у каждого варианта формулировки в генераторе датасета есть
срез (`dev` или `test`). Правила и пороги подбираются только на `dev`,
ML-классификатор обучается только на `dev`, а заголовочные цифры в README —
на `test`, чьи формулировки система до замера не видела. Рукописный срез
(`handwritten`) написан другим стилем и считается отдельной строкой.

## Структура репозитория

```
kz-contract-risk/
├── src/contract_risk/
│   ├── schemas.py            # доменные типы: пункт, находка, отчёт, роли сторон
│   ├── taxonomy.py           # категории и уровни риска, описания для отчёта
│   ├── config.py             # настройки из окружения (pydantic-settings)
│   ├── ingestion/            # ЭТАП 2 — извлечение структуры
│   │   ├── normalize.py      #   нормализация текста, склейка переносов, колонтитулы
│   │   ├── language.py       #   ru / kk по специфичным буквам казахского алфавита
│   │   ├── contract_type.py  #   аренда / поставка / подряд по ключевым словам
│   │   ├── loaders.py        #   TXT, DOCX (с восстановлением автонумерации Word), PDF
│   │   ├── ocr.py            #   точка входа для сканов (tesseract rus+kaz), не на MVP
│   │   └── segmenter.py      #   пункты и подпункты с иерархией нумерации
│   ├── corpus/               # ЭТАП 4 — эталонный корпус
│   │   ├── manifest.py       #   источники и лицензионный статус — проверяется кодом
│   │   └── audit.py          #   баланс сторон, утечка в eval, покрытие категорий
│   ├── retrieval/            # ЭТАП 4 — поиск похожих формулировок
│   │   ├── embeddings.py     #   hashing (офлайн) и multilingual-e5 (опционально)
│   │   └── store.py          #   in-memory и pgvector за одним протоколом
│   ├── rules/                # ЭТАП 5 — baseline на правилах
│   │   ├── lexicon.py        #   словари ролей и формулировок, ru + kk
│   │   ├── parties.py        #   кто обременён пунктом: сторона-субъект, «с Арендатора…»
│   │   ├── features.py       #   ставки пени, сроки, лимиты, суммы — числа из текста
│   │   ├── catalog.py        #   правила с примерами, которые тестируются автоматически
│   │   └── engine.py         #   прогон правил, документные проверки (нет форс-мажора…)
│   ├── rag/                  # ЭТАП 6 — сравнение с рыночной практикой
│   │   └── compare.py        #   похожие эталоны + разница признаков человеческим языком
│   ├── ml/                   # ЭТАП 7 — лёгкие классификаторы
│   │   └── classifiers.py    #   тема пункта и риск: TF-IDF + логрегрессия, объяснимые веса
│   ├── llm/                  # ЭТАП 8 — LLM со structured output
│   │   ├── classifier.py     #   LangChain + Claude, проверка цитаты, кэш ответов
│   │   ├── redact.py         #   ИИН/БИН, IBAN, телефоны, e-mail — до отправки в API
│   │   └── prompts/          #   версионированные промпты
│   ├── detectors.py          # ЭТАП 9 — null / rules / ml / llm / hybrid за одним протоколом
│   ├── pipeline.py           # файл → документ → находки → отчёт
│   ├── report/               # ЭТАП 10 — отчёт для не-юриста (HTML, PDF)
│   ├── evaluation/           # ЭТАП 1 — харнесс, метрики, датасет, генератор синтетики
│   ├── api/                  # ЭТАП 11 — FastAPI
│   ├── ui/                   # ЭТАП 11 — Streamlit
│   └── cli.py                # kzcr: eval / dataset / corpus / train / analyze
├── data/
│   ├── corpus/               # эталонные формулировки + sources.yaml (лицензии)
│   └── eval/                 # templates/ (генератор), dev/, test/, handwritten/
├── evals/results/            # JSON каждого прогона — строки EVALUATION.md восстанавливаются из них
├── docs/                     # план, архитектура, руководство по разметке, политика корпуса, правовые риски
├── scripts/                  # генерация датасета
├── tests/
└── db/init.sql, docker-compose.yml, Makefile
```

## Этапы

Статус каждого этапа и итог чекпоинта дописываются сюда по мере работы.

### Этап 0. Каркас, таксономия, руководство по разметке
- pyproject, ruff, pytest, Makefile, docker-compose с pgvector.
- `docs/LABELING_GUIDE.md`: категории, уровни, пороги («пеня выше 0,5% в день —
  высокий»), правило перспективы стороны. Пишется **до** правил: правила
  реализуют руководство, а не наоборот.

### Этап 1. Eval-харнесс и метрики (до системы)
- Формат эталона: пункт → категория, уровень, id ловушки; документные находки
  («нет пункта о форс-мажоре») отдельно.
- Метрики: detection P/R/F1 на уровне пункта, strict (пункт + категория),
  recall по высокому риску, точность уровня, ложные тревоги на чистых
  договорах, документные находки; бутстреп-интервалы по документам.
- Null-детектор и «оракул» как санити-проверки харнесса.

### Этап 2. Извлечение структуры
- TXT/DOCX/PDF → нормализованный текст → пункты с номерами, уровнем,
  родителем, разделом и смещениями в тексте (для подсветки доказательств).
- DOCX: восстановление автонумерации Word (python-docx её не отдаёт), таблицы.
- PDF: колонтитулы, переносы; скан определяется и помечается `needs_ocr` —
  OCR подключается как отдельный адаптер, а не молча.
- Двуязычные договоры (kk | ru в двух колонках): выбор языка анализа.

### Этап 3. Eval-датасет (заморожен до правил)
- Генератор из шаблонов с падежными формами сторон (ru и kk), варианты
  с разметкой `dev`/`test`, зеркальные ловушки (обременяют контрагента —
  для пользователя не риск), чистые договоры для замера ложных тревог.
- Рукописный срез: договоры другим стилем, размечены вручную.
- Проверка целостности: каждый размеченный пункт находится сегментатором.

### Этап 4. Эталонный корпус + pgvector
- Источники только с проверенным статусом: официальные документы
  (не охраняются по ст. 8 Закона РК «Об авторском праве и смежных правах»)
  и формулировки, написанные для проекта. Статус проверяется кодом.
- Баланс сторон: нейтральные формулировки + симметричные «в пользу А» /
  «в пользу Б»; аудит падает, если категория перекошена.
- Проверка утечки: ни один эталон не совпадает с текстом eval-датасета.

### Этап 5. Baseline на правилах
- Анализ сторон (кто обременён пунктом), числовые признаки, правила
  по девяти категориям, документные проверки. У каждого правила есть примеры
  «срабатывает / не срабатывает», они же — автотесты.
- Первая строка EVALUATION.md.

### Этап 6. RAG-сравнение
- Для каждой находки: ближайшие эталоны той же категории, «в норме — так,
  у вас — так», разница числовых признаков (ставка, лимит, срок уведомления).

### Этап 7. ML
- Тема пункта (маршрутизация для RAG и LLM) и вероятность риска для стороны.
  TF-IDF + логистическая регрессия: веса объяснимы (какие фразы повлияли).

### Этап 8. LLM со structured output
- Только для пунктов, которые правила не покрыли, а ML считает подозрительными.
- Pydantic-схема ответа, дословная цитата-доказательство (проверяется: цитаты
  нет в тексте пункта — находка отбрасывается), temperature 0, кэш ответов по
  хэшу входа, версия промпта в каждом ответе, маскирование персональных данных.

### Этап 9. Гибрид и сравнение конфигураций
- rules / rules+ml / rules+llm / hybrid на dev, test, handwritten.

### Этап 10. Отчёт
- HTML (и PDF через WeasyPrint): сводка, пункты по убыванию риска, цитата
  с подсветкой, «как обычно пишут», «что предложить контрагенту», дисклеймер.

### Этап 11. Продакшн-обвязка
- FastAPI (загрузка → отчёт JSON/HTML/PDF, без сохранения файлов),
  Streamlit, CI (ruff + pytest + pgvector), README с честными ограничениями.

## Чекпоинты

Формат: что сделано → чем проверено → решения, которые стоит пересмотреть.
Заполняется по ходу работы.

### ✅ Этапы 0–1: каркас, руководство, харнесс
- **Сделано:** руководство по разметке с порогами до первого правила;
  метрики (detection / strict / high recall / точность уровня / ложные тревоги
  на чистых договорах / документные находки) с бутстреп-интервалами по договорам;
  прогон пишет JSON с хэшем датасета и коммитом.
- **Проверено:** метрики — на вручную посчитанных случаях; харнесс — null
  (R = 0) и оракулом (F1 = 1).
- **Пересмотреть:** precision при нуле предсказаний — `None`, а не 0/1;
  если это мешает сводным таблицам, решать там, а не в формуле.

### ✅ Этап 2: извлечение структуры
- **Сделано:** сегментатор принимает номер, только если он продолжает
  нумерацию; «Статья N», «N-бап», приложения, реквизиты вне анализа;
  DOCX — пересчёт автонумерации Word и двуязычные таблицы; PDF —
  колонтитулы и определение скана; OCR (tesseract rus+kaz) отдельным адаптером.
- **Проверено:** 42 теста, включая реальный PDF (WeasyPrint → pdfplumber)
  и реальный OCR; 100% размеченных пунктов всех срезов находятся сегментатором
  во всех пяти стилях вёрстки генератора.
- **Юр. риск:** рендер страниц для OCR — pypdfium2, не PyMuPDF (AGPL).

### ✅ Этап 3: eval-датасет
- **Сделано:** генератор (270 договоров: аренда ru/kk, поставка, подряд;
  20% чистых; зеркальные ловушки; документные находки), рукописный срез (6),
  стресс-срез (6, написан против зафиксированных правил).
- **Проверено:** файлы в репозитории побайтно совпадают с генератором;
  формулировки ловушек test не встречаются в dev.
- **Пересмотреть:** шаблоны, правила и оба рукописных среза написаны одним
  автором — оценка оптимистична. Нужны публичные договоры (см. EVALUATION.md).

### ✅ Этап 4: эталонный корпус + pgvector
- **Сделано:** 80 формулировок (authored CC0), лицензия источника проверяется
  при загрузке; баланс сторон (нейтральных ≥ половины, стороны поровну);
  hashing-эмбеддер (офлайн) и e5 (опционально); in-memory и pgvector за одним
  протоколом, защита от поиска чужим эмбеддером.
- **Проверено:** аудит утечки нашёл 2 эталона, почти дословно совпавших
  с рукописным срезом, — переписаны; pgvector даёт тот же порядок выдачи,
  что in-memory (тест против настоящей базы).
- **Юр. риск:** шаблоны с коммерческих сайтов в корпус не берутся;
  госзакупочные формы — только с меткой перекоса в пользу заказчика.

### ✅ Этап 5: правила
- **Сделано:** анализ сторон по падежам (ru + kk), числовые признаки,
  14 правил + 2 документные проверки, у каждого правила примеры-тесты.
- **Проверено:** test до правки — P 1.00 / R 0.977; единственный тип
  пропуска («может быть изменена Подрядчиком») исправлен отдельным
  коммитом с раскрытием. Синтетика и рукописный срез насыщены (1.00).
  Стресс-срез: P 1.00 / R 0.44.
- **Вывод:** синтетика больше не различает системы; дальнейшие решения
  принимаются по стресс-срезу и, когда появится, по публичным договорам.
